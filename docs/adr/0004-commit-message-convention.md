# ADR-0004: Commit message convention

- **Status**: Accepted
- **Date**: 2026-05-19
- **Deciders**: Cute-Donkey

## Context

Free-form commit messages make `git log` and changelogs noisy.
Conventional Commits provides a tiny, parseable grammar that supports
automated changelog generation and is widely understood.

## Decision

All commits follow the [Conventional Commits 1.0.0
specification](https://www.conventionalcommits.org/en/v1.0.0/).

Allowed types:

| Type        | Use for                                             |
| ----------- | --------------------------------------------------- |
| `feat`      | a new user-visible feature                          |
| `fix`       | a bug fix                                           |
| `refactor`  | code change that neither fixes a bug nor adds a feature |
| `perf`      | performance improvement                             |
| `docs`      | documentation only                                  |
| `test`      | adding or fixing tests                              |
| `build`     | build system, dependency, toolchain changes         |
| `ci`        | CI configuration changes                            |
| `chore`     | maintenance that does not fit the above            |
| `style`     | formatting only, no semantics                       |
| `revert`    | reverts an earlier commit                           |

Format:

```
<type>(<optional scope>): <imperative summary, lowercase, no trailing period>

<optional body, wrapped at ~72 columns, explains *why* not *what*>

<optional footer(s): BREAKING CHANGE:, Refs:, Closes:, ...>
```

Scope, when used, is the crate name without the `delta-v-` prefix
(`ships`, `physics`, `config`, ...), or a top-level concern (`adr`,
`ci`, `docs`, `devcontainer`).

Examples:

```
feat(ships): add cargo hold capacity to ship type schema

docs(adr): adopt conventional commits

build: bump rust toolchain to 1.90 for edition2024 transitive deps
```

Breaking changes are marked either with `!` after the type/scope
(`feat(physics)!: switch to f64 world coordinates`) or with a
`BREAKING CHANGE:` footer.

## Consequences

Positive:

- Machine-readable history; changelogs and version bumps can be
  generated by tools (`git-cliff`, `release-please`, ...).
- Reviewers see at a glance whether a commit is a feature, a fix or
  maintenance.
- Encourages small, focused commits.

Negative:

- Mild upfront overhead until the format becomes habit.
- Tooling enforcement (commitlint, husky, ...) is not added in this
  ADR; conformance relies on review until it is.

Follow-up:

- An automated check (commitlint via CI or a Git hook) can be added
  later. Tracked in [`docs/workflow.md`](../workflow.md).
